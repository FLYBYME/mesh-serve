THIS IS A ONE-LINE FIX WITH A LARGE BLAST RADIUS

Adding `scopedBy: 'tenantId'` to `releaseCrud` changes every generated read and
write on that collection. Four things already use it and you must check each:

  * `cdn.compose` — reads `release.find_one` by hash to return an existing
    composition, and writes `release.create`. It resolves the caller's tenant
    itself (`callerOf`) and puts it on the row.
  * `cdn.deploy` — reads a release and compares `release.tenantId` to
    `site.tenantId`. If scoping makes that read return nothing for a legitimate
    caller, deploy breaks and the failure looks like a missing release.
  * `src/cdn/methods/rolling.ts` — runs from an EVENT, so it has no caller at
    all. It constructs a meta for the release's own tenant. Read the comment
    there before you change anything; it explains why that is the honest answer
    and not a bypass.
  * `release.find({ query: { rolling: true } })` in the same file sweeps ACROSS
    tenants deliberately, then filters. Scoping may silently narrow that to
    nothing, which would stop every rolling release working with no error
    anywhere. This is the one most likely to break quietly.

THE UNIQUE KEY MUST STAY GLOBAL

`unique: [{ fields: 'hash', scope: 'global' }]`. Two organizations composing the
same kernel and parts HAVE composed the same release — that is the property the
whole content-addressed model rests on. The framework's `normalizeUniqueKeys`
has rules about global keys on scoped collections; if it refuses, post a comment
saying exactly what it said before working around it, and do not quietly change
the key to scoped.
