THE TASK
================================================================================

`surf.surfdns.net` runs mesh-serve because I typed a page of shell commands at
it. Five more machines need the same, and by hand five more times is how a fleet
ends up with five subtly different boxes and nobody able to say which.

**One command, bare Ubuntu to running, safe to run twice.** Re-running converges
rather than duplicating — the same property `node.reconcile` has, for the same
reason: the thing you reach for when something looks wrong must be safe to reach
for.

Steps it owns: Node 22 + git if absent; clone or pull to a **pinned ref**;
`npm install` and `npm run build` on the box; `/etc/mesh/node.env` at mode 600;
the systemd unit from `deploy/`; enable and start; and **a verification step that
says whether the node actually came up** rather than exiting 0 because
`systemctl enable` returned 0.

--- Three things that are not style preferences ------------------------------

  * **Secrets never on a command line.** An argument is visible in `ps` to every
    user on the box. `surf` was provisioned by piping the env file over stdin
    into `cat > /etc/mesh/node.env`; that pattern works, keep it or better it.
  * **No `MESH_KEY` or `MONGODB_URI` in the repository** — not as a default, not
    in an example file with real-looking values. A placeholder somebody edits in
    place is a placeholder that ends up committed.
  * **Do not open the mesh port.** Exactly one machine has a public mesh port;
    every other node binds loopback and dials out to it. FLYBYME/surfdns#50 just
    landed making that binding actually work — **read what it does**, because the
    previous behaviour was that the host argument was ignored entirely and a node
    told to bind 127.0.0.1 bound every interface.
