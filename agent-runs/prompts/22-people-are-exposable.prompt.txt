================================================================================
WHERE THE ISSUE IS WRONG
================================================================================

The issue says: declare `visibility: 'public'` for the permitted actions, and
for `organization` and `role`, "if global, document/audit".

That is not enough, and step 2 is where it goes wrong.

`visibility: 'public'` means MAY BE EXPOSED. It never means unauthenticated —
that is the gate's job, in the site's grant. So flipping the flag is safe from
the "anonymous reader" angle and dangerous from a different one:

  * `organizationCrud` has NO `scopedBy`. Make `organization.find` exposable
    and any signed-in user of any site lists EVERY organization on the
    platform — every tenant's name, slug and id. That is a tenant leak, and
    it is exactly the bug `release.find` had (FLYBYME/surfdns#60).
  * `organization` cannot be fixed with `scopedBy: 'tenantId'`, because an
    organization IS the tenant. The scope is "organizations I hold a
    membership in", which is a JOIN, not a field on the row.
  * `roleCrud` is different and simpler: roles are a global catalogue with no
    tenant data in them. Reading them at a `user` gate is fine. Say so
    explicitly rather than by omission.
  * `membershipCrud` already has `scopedBy: 'organizationId'`, so it is the
    one the issue describes correctly.

THE TASK
================================================================================

Make the `people` application exposable without leaking one tenant to another.

1. `membership` — declare the exposable actions (`find`, `findOne`, `get`,
   `count`, `create`, `delete`). Its existing `scopedBy: 'organizationId'`
   does the work. Verify that it does, with a test that a caller scoped to
   org A gets zero rows for org B — not that it errors, that it gets zero.

2. `role` — declare `find`, `findOne`, `get`, `count` exposable. Global, and
   deliberately so. Put the reason in a comment on the contract, not only in
   the PR.

3. `organization` — the real work. A signed-in caller must see the
   organizations they are a member of, and no others. Decide how, and argue it
   in your plan comment BEFORE writing code. The options as I see them:

     a. a dedicated tool, `identity.my_organizations`, that resolves
        memberships then reads organizations. `organization.find` stays
        internal. Smallest, most obviously correct, and the client asks a
        question it actually has ("which orgs am I in") instead of filtering.
     b. a scope resolver on the CRUD itself, so `organization.find` gains a
        membership-derived filter. More general, and it puts a join in the
        scoping path, which nothing else does.

   I would take (a). If you take (b), say why and show where the join happens.
   `organization.create` is a separate question from reading — a signed-in user
   creating an organization is a real flow, and it does not need a scope.

4. Whatever you choose, `mesh-serve client` must regenerate cleanly —
   `describeExposure` at `descriptor.js:48` currently throws on these
   contracts, and "it generates" is the acceptance test the operator console
   is blocked on.

================================================================================
THE TEST THAT MATTERS
================================================================================

Two organizations, a user who is a member of exactly one. Then, for every
action you declared exposable:

  * the member sees their own org's rows
  * the member sees ZERO of the other org's rows — not an error, zero
  * an unauthenticated caller is refused

A test that only proves the happy path proves nothing here. The bug class this
is preventing is "it worked, and it also returned somebody else's data".

`test/api/visibility.test.ts` is where the existing shape of this lives.
