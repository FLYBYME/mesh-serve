The CLI is the platform's front door and it fails at the two things a front door
must do: tell you what it offers, and fail comprehensibly. Six defects, all
measured in ordinary use on 2026-09-11 by the person who owns this platform.

**Start from `master`.** `dispatch/23` attempted part of this and is not the base.
Read it for reference — `git show dispatch/23` — its legacy-index error message is
worth keeping and its approach to the rest is not: it deleted 88 lines of
explanatory comments out of `bin/node.mjs` while editing it with regex scripts.

Reading list, and you should not need much beyond it:

    stuff.md                 repository root. Items 10-17 are this dispatch,
                             written after he read the code himself.
    spec/cli.md              the design, already argued
    bin/mesh-serve.mjs       118 lines. The dispatcher.
    src/cli/run.ts           404 lines. The site projection — the half that IS
                             built the way spec/cli.md wants.
    src/cli/descriptor.ts    234 lines. Two of the six defects live here.
    src/bring-up.ts          228 lines. `seed`, and its own flag parsing.

--------------------------------------------------------------------------------
1 — `--help` STARTS A NODE

    $ npx mesh-serve node --help
    connecting to mongodb://localhost:27017/mesh-serve ... ok
    [MeshApp starting...]                 ← it started a database node

    $ node bin/mesh-serve.mjs seed --help
    Bring-up failed: No password. …       ← it tried to seed a cluster

`bin/mesh-serve.mjs` branches on the subcommand name and nothing looks for
`--help` or `-h`. The two commands that change the most state answer a request for
documentation by doing the thing.

**`--help` is answered before any command runs**, for every subcommand. Each
subcommand's help names its own flags. They are not guessable: `node` takes
`--ws --cdn --api --mcp --db --service`; `seed` reads fifteen.

### Use `commander`

The owner asked for it and the reason is in the code: flags are hand-parsed with
`indexOf` in **three** separate places — `bin/mesh-serve.mjs`, `src/bring-up.ts`,
`src/cli/args.ts` — and each gets a different subset of the job right.

**One thing to be careful about**, and it is `spec/cli.md` §1's whole argument: the
site projection has **no fixed list of subcommands.** What
`mesh-serve --host … <domain> <action>` accepts comes from that site's own
`_describe`, resolved at run time — *"the commands are the contracts"*. Use
commander for the fixed build-time set (`node`, `seed`, `client`, `publish`,
`dev`) and keep the dynamic half resolving from the exposure. If commander can
carry both cleanly, use it for both; if making it do so means declaring a command
list a *site* is supposed to decide, use it for the fixed part and write the
reason in `spec/cli.md`. **Do not flatten the dynamic half to make the parser
tidy.**

### And refuse unknown flags

`src/bring-up.ts` has a comment about this, written after `--policy` was typed,
not recognised, silently ignored, and the seed reported success having set no
policy: *"An unknown flag being ignored is the shape to be angry about."* It made
the known-but-malformed case loud and left the unknown case silent. Close it.

2 — WITH NO `--host`, DEFAULT TO THE CONTROL SITE

    $ npx mesh-serve login
    A node is running, and no site serves console.localhost:8080.

`currentHost()` is `MESH_HOST ?? read().current` — the last host you logged into.
On a fresh machine that is nothing, and you get *"Which site?"*.

**Default to `127.0.0.1`.** The control site is the one site that always exists:
the node creates it at boot and it is the only thing reachable before anything has
been seeded, which is exactly when a person needs the CLI. Keep `--host` and
`MESH_HOST` ahead of it, and say in the help which one answered.

3 — THE RECOVERY MESSAGE NAMES A FLAG THAT DOES NOT EXIST

`src/cli/descriptor.ts:135` prints:

      mesh-serve seed --org-slug <slug> --org-name "<name>" \
        --host console.localhost \
        --api http://console.localhost:5005 \
        --app-repo <a git url or bare repo> --parts <part>

**`--app-repo` appears exactly once in this repository: in the message telling you
to type it.** `bring-up.ts` reads `--repo`. And it ignores unknown flags, so
following this instruction seeds with **no repositories at all**.

The same four lines are wrong twice more: `--api` is the URL the served page will
call, not the node you sign in to — that is `--control`, and passing `--api`
instead signs in against the default `127.0.0.1:5005` and reports *"Those
credentials are not valid"* while the node you meant runs in front of you. And
`--password` is missing, which `seed` cannot run without.

**Test this one.** A test that checks the suggested command against the flags
`bring-up.ts` actually reads is the only kind that can catch it, and it would have
caught all three. A recovery instruction that cannot be followed spends the
reader's trust before it spends their time.

--------------------------------------------------------------------------------
4 — THE PLATFORM EXPLAINS ITSELF PERFECTLY AND THE CLI THROWS IT AWAY

This is the best of the six, because the hard half is already right.

    $ npx mesh-serve whoami
    http://127.0.0.1:5005/_describe answered 403.

What the server sent, verified with curl against the same node and ticket:

    {"error":"PROVISIONAL_ACCOUNT",
     "message":"This account was created on first boot and can do nothing until
                its password is set. Set one, and it becomes an ordinary account."}

`src/cli/descriptor.ts:116`:

    if (!response.ok) throw new CliError(`${url} answered ${String(response.status)}.`);

**The body is discarded and the status code is printed.** Every refusal this
platform is careful about arrives at the person who needs it as three digits.

Worse: the CLI already has the way out. `set-password` is a built-in in `run.ts`,
written for exactly this account, with a comment explaining that a provisional
caller's descriptor is nearly empty by design. The one command that fixes the
situation was unreachable because the message naming it was dropped.

Fix `fetchDescriptor` to read the body and render `error` and `message` when they
are there, then check the rest of the CLI for the same shape.

While you are here: the provisional gate refuses **ahead of every level including
`public`** (`src/api/methods/gate.ts:263`), deliberately and documented. So
`_describe` answers 200 with no ticket, 200 with a *garbage* ticket, and 403 with
a real provisional one — being signed in as the account the platform just made for
you is the only state where the public endpoint refuses. Decide whether
`_describe` should be exempt and write the argument either way; if it stays, the
message matters more, not less.

--------------------------------------------------------------------------------
5 — ONE SITE, TWO CREDENTIAL RECORDS

`~/.mesh-serve/credentials.json` holds both:

    http://127.0.0.1:5005      ticket issued 2026-09-11T20:08
    127.0.0.1:5005             ticket issued 2026-09-10T19:49

Same site, two keys, two tickets. So signing in through one spelling leaves the
other stale, `logout` forgets one of them, and which ticket a command uses depends
on how the host was typed that time. Normalise the host in one place before it is
used as a key, and handle the duplicates already on disk.

6 — `login` SUCCEEDS AND LOOKS LIKE IT FAILED

    $ npx mesh-serve login --host http://127.0.0.1:5005
    email: operator@node.invalid
    password: $

The shell prompt returns on the password line and nothing else prints. `run.ts`
does print `Signed in to … as …` and `Ticket stored in …`, and the ticket **was**
written — the credential file shows it, issued that minute. So the output exists
and does not survive the hidden-password prompt, which sets `rl.output.write` to a
no-op and juggles raw mode around the read.

Find what swallows it. Test by driving the entry point with scripted stdin, not by
calling `login` directly — the whole defect is in the plumbing around the call.

7 — A DATABASE FROM AN OLDER VERSION CANNOT START

    [BootOrchestrator] Boot sequence aborted due to error: { error: 'Index already exists with a different name: email_1' }
    MongoServerError: Index already exists with a different name: email_1
        at Connection.sendCommand (…/mongodb/lib/cmap/connection.js:306:27)
        … 9 more frames …
      code: 85, codeName: 'IndexOptionsConflict'

`email_1` is mongo's default name for an index on `{email: 1}`. A database created
by an older version of this code has one; today's code creates the same index as
`uniq_user_email`; mongo will not rename, so it refuses with code 85 and the boot
aborts with a driver stack trace.

mesh catches only code `11000` (duplicate data) and rethrows the rest untouched.
**mesh is frozen**, so the handling is on this side, where the indexes are
declared. Name the database, the collection and the index, and say what a person
can do. Every option is destructive-adjacent — drop it, rename it, use another
database — so decide whether this is a refusal with instructions or a migration
behind an explicit flag, and write the argument in `spec/roadmap.md`.

`dispatch/23`'s version of this message is a good starting point.

Reproduce it before fixing it, in a scratch database. **Do not touch a live one.**

--------------------------------------------------------------------------------
WHAT NOT TO DO

- **Do not start, stop or reseed a cluster on ports 4001/5005/5006/8080.** Scratch
  ports and a scratch `--db` for anything you run. `RUNNING.md` has the commands
  and every one of them was verified today.
- **Do not delete comments.** `dispatch/23` removed 88 lines from `bin/node.mjs`
  recording why fleet stays direct, why the switchable set lives in code, why
  telemetry is switchable. If a comment is wrong, fix it; if it is in your way,
  it is not.
- Do not touch `@flybyme/mesh` (frozen), or the other repositories.
- Do not add a second list of subcommands. That is `spec/cli.md` §1's argument.
- `as any`, `as never` and `!` are bugs here, not style nits.

--------------------------------------------------------------------------------
HOW TO EDIT, AND WHY THIS PARAGRAPH EXISTS

**Edit files with your file tools.** Three dispatches in a row have committed
programs that rewrite source with regular expressions — eighteen `.cjs` in
mesh-core, five `patch_*.js` here, six more in mesh-core the same evening. All
deleted by hand, twice by the owner of this platform, who found them himself.
Write the change. Do not write a program that writes the change.

**Commit as you go, in the foreground.** A dispatch here reported SUCCESS with
eight modified files unstaged and nothing committed. When your turn ends the
process exits.

**`git status` must be clean when you finish.**

  command's flags and **start nothing**. A test asserts it by running the entry
