================================================================================
THE TASK
================================================================================

**F6 — `publish-cli` mints its own caller, and nothing checks it.**

The CLI joins the cluster as a **node**, and *a node must never hold a user
credential*. So it mints `meta: { user: { id: 'cli', tenant_id: args.publisher } }`
from its own `--publisher` flag, and until dispatch 10 the publish path trusted
that string.

**B6 closed the trust half.** `catalog.publish` now derives the publisher from
`ctx.meta.user.tenant_id` and refuses a call with none:

```
Publishing a part changes what runs on hostnames resolving to it, so it
requires an authenticated caller. This call carries none.
```

**Which means the CLI now works only because it lies convincingly.** It supplies
its own `tenant_id` and the server believes it, because the server has no way not
to. Give it a real credential and the loop closes.

The same gap in a different shape, and worth reading first — the roadmap entry
quotes it:

```
$ npx mesh site find --bootstrap ws://127.0.0.1:4001
Error: Scoped collection "site" requires a resolved "tenantId" scope, but none
was provided in call context.
```

That is **both halves working as designed**: `ToolCommands.ts` passes no
`meta.user` because a node has none, and `site.find` refuses because D3 says a
scoped read needs a resolved scope. Neither is broken. What is missing is the
thing in between.

================================================================================
WHAT TO DECIDE, AND ARGUE
================================================================================

**Where the credential comes from.** `apiToken` already exists as a collection
and `hashApiToken` is in `src/identity/module.ts`. An environment variable is the
obvious carrier — `bin/node.mjs` already reads `GIT_TOKEN_<HOST>` for private
clones, and `src/catalog/tools/publish.ts`'s sibling `A5a` records **why the
token never goes in a URL**: it reaches `.git/config`, git's error messages, and
therefore the build log, which is stored on the build row and travels with the
failure. The same reasoning applies to anything a CLI prints.

**How a token becomes a scope.** The token identifies a principal; the *scope* is
an organization resolved from that principal's memberships. `bin/node.mjs`'s
`authorize` hook already does exactly this for HTTP callers — read it and decide
whether the CLI path should reuse it or whether a mesh caller resolves differently.

**What happens with no token.** It must **refuse and say what is missing**,
naming the variable. A publish that silently succeeds with no credential is what
this dispatch exists to remove, and a confusing failure is only marginally better
than a silent success.

**Whether `--publisher` survives.** After this it is derivable. A flag that looks
authoritative and is not is worse than no flag — but it may still earn a place as
an assertion the CLI checks locally before spending a round trip.

================================================================================
WHAT NOT TO DO
================================================================================

**Do not give the node a user credential.** The rule is real: a node holding a
user's credential can act as that user for anything, on any call, forever. The
credential belongs to *the invocation*, not to the process's identity on the
mesh.

**Do not change `catalog.publish`'s checks.** B6 landed. This makes the CLI able
to satisfy them honestly.

**Do not build a login flow.** A token from the environment is enough. How a
person obtains one is a console feature and not this.

**Zero casts.** Foreground commands, commit as you go.
