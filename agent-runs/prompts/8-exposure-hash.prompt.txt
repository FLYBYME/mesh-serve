THE DECISION THIS TASK IS REALLY ABOUT — READ BEFORE WRITING CODE
================================================================================

There is a contradiction sitting between two things that are each correct, and
resolving it *is* the task. Do not code past it.

**1. A release is site-independent, by design.** C1: `tenantId`, `name` and
`composedAt` are deliberately not inputs to the release hash, because *two
organizations composing the same set have composed the same thing.*

**2. The gate is per site, as of D2.** One site may expose `domains.zone_find`
as `public` while another requires `user`, on the same release.

**So an exposure hash computed over gates cannot live on the release.** Two sites
sharing one release at different gates would need one field to hold two values.
`release.exposure` as currently commented — *"the exposure this release's parts
were generated against"* — may therefore be the wrong home for it, and saying so
is a legitimate outcome of this dispatch.

The other half of the contradiction is already written down in
`src/api/client-cli.ts:113-125`, and it is the clearest statement of the problem:

> `auth: 'public'` for every entry, and it is **not** a gate being granted. A part
> declares what it *calls*; a site declares what it *exposes and at what level*.
> … **the exposure hash in this file is not the site's.** A site's hash is
> computed over real gates. So a part's hash cannot be compared against what an
> API reports, and the check has to happen at compose time, where the site's
> grants are actually known.

**There are two different hashes here and they are being called one name.**

- **a shape hash** — the contracts and their request/response schemas. Identical
  for everyone, belongs to the release, and is what actually answers *is this
  generated client stale?*
- **a gate hash** — what this site exposes and at what level. Per site, changes on
  a deploy without any part changing.

Decide which one D4 needs, whether both are needed, and where each lives. State it
in the report before describing the code. If the answer is that
`release.exposure`'s comment describes a field that cannot exist as written, say
that plainly — a wrong field with a confident comment is exactly what
`spec/unread.md` exists to catch, and shipping a second one would be worse than
shipping nothing.
