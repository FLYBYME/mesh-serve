THE TASK
================================================================================

Read the issue. **Build the SERVER half in this repository** — the ingest
contract, the collection, the file sink, and the per-site configuration. The
`telem` Extension itself is mesh-core and is somebody else's dispatch; design the
contract so a browser can implement against it, and say in your plan comment
exactly what shape you settled on so they can.

THE TRANSPORT IS DECIDED, DO NOT REOPEN IT

Browser to API is HTTP and SSE. SSE is one-way DOWN — there is no browser
WebSocket and that is deliberate (`src/api/methods/stream.ts:4`: everything flows
one way, so a duplex transport buys a protocol upgrade, a framing layer and a
reconnect story in exchange for nothing). Telemetry flows UP, so it is a batched
POST. Do not add a WebSocket.

WHAT MAKES THIS DIFFERENT FROM A CRUD COLLECTION

  * It is written by anonymous callers. A page that has not signed in still
    boots, still fails, and is exactly when you want the logs. So the ingest
    contract has to be callable at `public` — and that is a hole unless you
    bound it. Say in your plan how you bound it.
  * It is high volume and low value per row. Everything else in this repository
    is the opposite. Bounded writes, and a story for retention.
  * **It must reach a file as well as a collection.** The database being
    unavailable is precisely when logs matter, so a sink that only writes rows
    is a sink that goes quiet in the incident.

CONFIGURABLE MEANS PER SITE

From the site record, like `mesh` and `policy` — not a constant, not an
environment variable on one node. A logger nobody can turn down is a logger
somebody turns off.

PRIVACY IS PART OF THE DESIGN, NOT A REVIEW STEP

Never store ticket values, passwords, or form contents. Call keys and outcomes,
not inputs. Write down in your closing comment what you send and what you
deliberately do not — that list is the deliverable as much as the code.

ALSO: THE SERVER'S OWN HTTP REQUESTS

The cdn and the api should log the requests they serve — method, host, path,
status, duration. They currently log almost nothing per request, so a 404 or a
401 leaves no trace at all. Same sink, so one query answers "what happened to
this session" across the browser and the two servers. Keep it cheap; this is on
the hot path.
