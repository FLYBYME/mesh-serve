## The recurring failure: `stale`

Hit for the third time today. It is not a bug in one place, it is a design
consequence, and it needs to stop being manual.

**What happens.** A generated client bakes one `shapeHash` covering the site's
**whole** exposure. Add any contract anywhere — `site.create`, `cdn.site_edit`,
`node.provision` — and that hash moves, so **every deployed part is instantly
stale**, including parts that do not use the new contract and could not care that
it exists. The catalog browser breaks because the fleet gained a call.

The manual fix is: regenerate the client, bump every API-facing part, publish,
build, compose, deploy. Six steps, and I have run them five times today.

**Three fixes, in order of value:**

1. **Staleness should be per call, not per exposure.** *Did any call I use
   change shape?* — not *did the exposure change at all?* Adding a contract would
   then invalidate nothing, and changing one would invalidate only the parts
   using it. This removes the failure rather than reporting it better.
2. **`cdn.compose` should refuse a stale part**, naming it. A release that will
   fail in front of a person should not be composable. Fail at compose, where
   somebody is looking.
3. **A stale client should refetch the descriptor and recover.** #47 landed
   *reporting* what moved; recovery is still manual.

Until (1), every contract addition costs a full rebuild of every part.

# Late: the window model was the wrong shape, and that was the real finding

The console works and is unusable on a phone. Both are true, and the second is
not a polish problem:

> 99% of apps are not like gimp. even photoshop is not like gimp. but every
> "app" we build is like gimp. i just dont get it.

GIMP made every panel a floating window; everyone else made one window with
navigation inside it. **This platform handed authors GIMP**, so that is what got
built — four consoles, four windows, `catalog/index.ts` at 650 lines and
`releases/index.ts` at 581, each rebuilding its own shell.

The cause was in the type. `ViewDecl` carried `tile`, `defaultSize`, `minSize`
and `closable` at the top level: **four of its six fields described window
furniture**, so a view — a pure function from state to a description — was
invited to declare pixels. The type said windows, so authors wrote windows.

## What was done about it

**The seam** (mesh-web `f08dd7b`). Those four move into an optional `window`
object that a windowed chrome reads and a routing chrome ignores entirely,
losing nothing. `src/window/sink.ts` was the *only* code in the kernel reading
them, which is what made the move cheap and what proves they were misplaced.

Grouping alone was not enough, and this is the part worth keeping: a view
declared as a class property is inferred and checked structurally, so extra
properties are **allowed** — every stale declaration kept compiling and was
silently ignored. Two tests did exactly that; the only symptom was a 240px
window arriving at 480 and a tiled layout with nothing in it. Typing the old
names `never` turned it into an error naming the field, and immediately caught
**four more files**, one hidden behind `as unknown as`.

**`cx.display`** (mesh-web `ec3a54c`). How much room there is, as a signal. The
kernel has measured this all along — a `resize` listener and a `ResizeObserver`
in `start.ts` — and handed it to exactly one consumer, the window manager. So
the only thing that could react to available room was the thing that draws
windows. Deliberately a size and **not** `isMobile`: a width is a fact, what to
do at 380px is a decision, and it belongs to whoever is drawing. Also measured
once at boot, which nothing did — without it the display read 0×0 until somebody
dragged something.

**`touch-action: none` on `.titlebar`.** The drag handler was already
touch-correct (`pointerdown` + `setPointerCapture`), but the browser claims the
gesture for scrolling before the handler runs. `.grip` had the property and the
titlebar did not, which is why resizing worked under a finger and dragging did
not. That was the whole of *"i cant drag a window in mobile"*.

## Routes are views, and nobody has to declare them twice

A window record is `(owner, view, params)` — that triple is already an address,
and a URL is only its serialisation. Two things make it work with no new
declaration: `params` is `Record<string, Json>`, serialisable by construction
because the window manager already required it; and `declaredBy` is the manifest
name (`catalog`) as distinct from `id`, a pid. A second route registry would be
a second copy of what views already say, and the second copy goes stale.

`instances: 'many'` was the one real tension — two windows, same view, same
params, one URL. **Answer: the URL names the view with focus.** `focused()`
already exists on the manager, so it is a read rather than new state.

## What writing them found

An app spec catches a missing feature. Only a view spec catches these:

- **`declarationCard` opens blank against a part that already has a
  declaration**, and saving writes the blanks over it. Data loss.
- **`releasePartCard` and `releaseRepoCard` publish with no confirmation.**
  `release_repo` emits N `partReleased` events and rolling releases follow them,
  so one click can move every rolling site.
- **`importRepoCard` sits in the DETAIL pane**, which needs a selection — so it
  is unreachable from an empty catalog, the only time it is needed.
- **badges default an unknown state to red**, so a `building` added server-side
  shows in the colour of `failed` without anybody deciding. `built` and
  `extension` are also the same green.
- **`site.create`, `group.create`, `group.update` are exposed and have no UI at
  all.** `site.create` for weeks. There is no way to create a site in a browser.

And the structural one: **five of the eleven catalog view files are one
component written five times**, with five status signals differing only in a
verb, none of which has a `refused`.

## The three gaps behind all of it

A rule every screen must follow, with nothing in the vocabulary to follow it
with — mesh-core roadmap U1, U2, U3, and surfdns#74:

- **no design tokens.** `badges.ts` holds eight literal hex colours while its
  neighbours use `var(--ink)`. Two colour systems in one directory. This is why
  two screens can follow every rule and still not match: the rules govern
  behaviour and nothing governs appearance.
- **`EntityListStatus` cannot say `unauthenticated` or `refused`.** The proof is
  in the code: `partsList.ts` sets `idleMessage: 'Sign in to view catalog
  parts.'`
- **no component expresses a refused or a busy control**, so rules §3 and §4 are
  hand-rolled or ignored.
